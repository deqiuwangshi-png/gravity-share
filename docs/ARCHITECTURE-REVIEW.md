## 二、当前架构全景

### 分层结构（四柜 + 双层组件）

```
app/            页面柜：marketing(6) / auth(4) / app(5 页 + 2 动态)
styles/         样式柜：globals + marketing(3) + auth(2) + app(10)，按访问区 + 组件分文件
components/     组件柜：common(2) / marketing(1) / app 下 shell(6)·discovery(3)·square(3)
lib/            数据柜：data(167) types(107) config(34) icons(27) text(24) discovery-store(22) square-store(21)
```

### 数据流（单向 + 事件驱动）

```
lib/data.ts（预置 seed）→ 内容池（内存态 store）
  → client 组件（发布/筛选/详情/广场）→ 页面渲染
发布时：publishDiscoveryItem / publishSquarePost → dispatchEvent → 消费端重渲染
```

- **依赖单向**：页面 → 组件 → lib，无反向、无循环；
- **数据收敛**：全部 mock 在 `lib/data.ts`（167 行），内容池对外 5 个引用点，无散落数据；
- **职责分离**：发现（对"东西"）/ 广场（对"人"）/ 推广（合规标识）/ 详情（决策 + 互动）边界清晰。

### 关键设计决策回顾（均已在代码中兑现）

| 决策 | 落点 |
|---|---|
| 前端模拟优先，后端冻结 | ARCHITECTURE.md §8 + 冻结清单 |
| 引用不托管（内容回流原平台） | 外链预览卡 / URL 链接即出口，无内容托管 |
| 商业透明（B 端标识 + C 端避险） | promo-note 警示行 + 详情页 detail-promo-note |
| 列表出线索、详情做消费 | 3 列社交卡（头像+正文 2 行）→ 详情动态页 |
| 无状态库、无过度设计 | 事件联动替代全局状态库，store 仅 20 余行 |

## 五、优化建议与演进方向

### 演进路线（延续"架构是涨出来的"）

```
阶段 0（当前，验收中）→ 阶段 1（接后端）→ 阶段 2（规模化）
```

- **阶段 0 收尾**：V2 视觉走查（唯一待办）→ 文档同步（P1-2）；
- **阶段 1 触发**：界面布局验收通过 + 业务方确认启动后端（ARCHITECTURE.md §8 双条件）；
- **阶段 1 必做**：内容池 → 数据访问层（fetch）；DTO 收敛；评论归一；client 化回退；
- **阶段 2 触发**：页面 > 20 / 组件 > 30 → 测试 + CI + 安全头。

### 架构治理建议（三条）

1. **文档即契约（强化）**：今日大量演进中，文档同步滞后了 1 轮（linkified-text/common、detail.css、短格式）——建议把"文档同步"纳入提交自检（治理规则 R4），每次改结构必须同步 ARCHITECTURE.md + SYSTEM-ARCHITECTURE.md；
2. **结构红利已吃满**：四柜 + 双层组件 + styles 对应关系是当前最大资产，后续所有新增页面/组件照章归位即可，无需新规则；
3. **唯一要守的边界**：mock 内容池是"临时机制"不是"架构组件"——任何新需求不要基于内存池做持久化假设（如收藏、历史记录），此类功能一律等接后端。

## 六、总体结论

从 v1 到 v2，架构完成了三次关键跃迁：

| 跃迁 | 状态 |
|---|---|
| 三层裸结构 → **四柜治理**（styles 归位、components 双层、CSS 全达标） | ✅ 已闭环 |
| 静态 mock → **发布/展示实时联动**（内容池 + 事件，无状态库） | ✅ 已闭环 |
| 物件索引卡片 → **社交动态页**（人 + 内容 + 互动 + 合规标识） | ✅ 已闭环 |

**当前架构对"纯前端 mock MVP + 快速产品迭代"是最优解：结构清晰、规则闭环、无债务堆积。** 剩余风险全部集中在"接后端"的转换点，且已识别出明确的前置改造清单（P1 五项）——届时按清单执行即可，无需推倒重来。
